FThe data feed, and what it does when it cannot reach anything

Nobody has to check this site by hand. Every number is fetched from docs/data/*.json; those JSON files are generated by scripts/refresh_feed.py from evidence/ in the repo plus, when the network is available, the live public leaderboard. A GitHub-hosted workflow runs it four times a day and on every push to the fetcher.

F2Why the fetch does not happen inside the analysis box

The environment this repo was analysed in has no outbound network at all: curl https://www.drivendata.org/ fails with SSL_ERROR_SYSCALL and urllib reports the TLS connection being closed. That is why the live fetch lives in .github/workflows/feed.yml — a GitHub-hosted runner with normal egress — and why refresh_feed.py falls back to a dated, verified snapshot (registry/leaderboard_snapshot_2026-10-06.json) instead of either failing silently or inventing rows.

Three consequences, stated because each one is a way a site like this usually starts lying:

  • If the fetch fails, the page says “unreachable — serving the last verified snapshot” and shows the snapshot's own timestamp. The staleness is the point of showing it. This has already happened once, for an instructive reason: the first scheduled run reached the board and got HTTP 200, then parsed zero rows, because the leaderboard table is rendered client-side and is not in the server HTML at all. The strict parser raised instead of publishing an empty board, and the fallback did its job — see IR-52-016. Treat “live board” here as live-attempted, snapshot-served until an endpoint that returns the board as data exists.
  • The workflow commits only docs/data/. It never touches docs/downloads/ or submission/: publishing a candidate raster has to stay a deliberate act, because a submission slot is spent once a week and cannot be recalled.
  • The board publishes a team name and a score, nothing else — no filename, no hash, no upload receipt. So no file-to-score mapping on this site is organiser-authenticated; where the site says “the 0.2778 file was h33-2-b2”, that is an owner report from a sibling session, and it is labelled as such on the irregularities page.

F3Run it yourself

python3 scripts/refresh_feed.py            # offline: evidence -> JSON
python3 scripts/refresh_feed.py --fetch    # also re-scrape the public leaderboard
python3 -m http.server 8080 -d docs        # then open http://localhost:8080/feed.html

The fetcher is stdlib-only on purpose, so a scheduled refresh cannot fail on a package index. Its parser prints a loud error if the leaderboard table comes back with an unexpected shape rather than publishing a short or empty board.
