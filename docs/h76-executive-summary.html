If you decide to submit it: the exact steps

  1. Download h76-candidate.tif (140,555 bytes) or the ZIP. Both are the same bytes; the ZIP exists because the organiser’s form accepts either a single-band GeoTIFF or a ZIP containing one.
  2. Check the file you actually downloaded on the browser checker. It decodes every pixel locally and reports each published rule as PASS or FAIL. Confirm the SHA-256 is 17c3f8325ac6f267b1b8cc58bc6fd9495c118c30de64d5f78293d19d7f20c907 — if it is not, you downloaded something else (a truncated file, or an HTML error page saved with a .tif extension, which is the most common cause of a confusing rejection).
  3. Sign in at the competition problem page and open Submit.
  4. Upload the file. The form rejects anything whose predicted values fall outside [0, 1] with Predicted values must be in range [0, 1]. This file’s values are exactly {0, 1} with 0 NaN and 0 infinite, so it cannot trip that rule.
  5. Name it h76-dva2vsa-B-37654px-20261009T213414Z.
  6. Note (140 of 140 characters): H76: View-B + 50 DVA-2 + 10 variogram/strike-alignment channels; 8-dir integer fan, lags 100-600m; 200m catalogue ring excluded; binary dots
  7. Wait for the score. The public chunk is scored on upload; the Initial Prize Round is scored on the private chunk, and one submission must be selected for both rounds before the deadline.

This repository cannot do steps 3–7. It has no DrivenData credentials, so it has never downloaded the competition data from the organiser and has never uploaded a file. Every score quoted here is either ORGANIZER-CONFIRMED from the public leaderboard or OWNER-REPORTED by the owner team. Nothing on this page is an organiser acceptance receipt.

Why the [0, 1] rejection happens, and how to diagnose it in seconds

The organiser’s message Predicted values must be in range [0, 1] has four realistic causes. In order of likelihood:

CauseHow to recognise itFix
The file you downloaded is not the file you think it isSHA-256 differs; or the file is a few hundred bytes; or a text editor shows HTMLRe-download. A GitHub Pages 404 page saved as .tif is the classic case.
Values are unnormalised model scores (log-odds, distances, z-scores)The browser checker reports min/max far outside [0,1]Normalise to [0,1] before writing, or emit binary {0,1}.
Wrong dtype — float64 or int16 instead of float32The checker reports BitsPerSample 64 or 16, or SampleFormat not 3Write dtype='float32'.
A NoData sentinel outside [0,1] (e.g. -3.4e38) inside the footprintThe checker reports a huge negative minimum and a GDAL_NODATA tagWrite NaN or 0 outside the footprint, never the float32 sentinel.

An audit of every raster this repository serves (110 TIFs and 82 ZIPs) found none of these defects, so the rejection the owner hit did not come from a current artefact here. That is recorded rather than papered over: the most likely source is a file from a sibling site or a truncated download. The browser checker exists so this can be settled in seconds, on the exact bytes you are about to upload.

The rules, quoted

From the official problem page, fetched 2026-10-09: predictions are pixel-wise probabilities in [0, 1]; the submission must use the same projected CRS as the training data (UTM zone 11N, EPSG:32611), the same 100 m resolution, the same bounds with null or NaN outside them, a single layer, and 32-bit float. Distances are weighted by a triangular kernel k(d) = max(1 − d/R, 0) with R = 300 m, and the score is the distance-weighted Tversky index TI(α, β) = TP / (TP + α·FP + β·FN) with α = 0.2 and β = 0.8.
