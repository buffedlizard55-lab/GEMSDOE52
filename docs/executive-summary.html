The steps

  1. Download. Click the TIFF button above (or the ZIP — the portal accepts “a single-band GeoTIFF (.tif) file, or a .zip file containing a single GeoTIFF”).
  2. Go to the submission page: competitions/306 → New submission. You need a DrivenData account that has accepted the competition rules.
  3. Choose the file you just downloaded.
  4. Paste the note (optional but it is how you tell submissions apart later): 
    H60 union_max 37654px; two-view co-training on SHA-pinned bytes; independence measured; >200m ring excluded; all-finite binary [0,1]; not a verified fault map
  5. Submit. The portal validates CRS, shape and geotransform against sample_submission.tif and checks that every value is in [0, 1].

Why the earlier “Predicted values must be in range [0, 1]” rejection happened

It was not a scaling error. The competition page says “data outside the bounds is null or nan”, so an earlier export wrote NaN outside the data footprint — and a NaN fails any range comparison. This repository now exports 0.0 outside the footprint instead, and gems52.grid.write_geotiff refuses to write a single non-finite pixel and then re-reads the file it wrote. The proof is re-read from the served bytes at publish time:

What this repository will not claim: a leaderboard score. The portal is login-walled, so no score in this repository is organiser-authenticated, and the local hide-and-recover instrument recovers held-out catalogue segments — the competition truth is expert-labelled faults that are not in the catalogue. The preregistered slot rule is “arm must beat the matched-budget random control in >= 3 of 4 hide-and-recover folds; among those, highest mean DTI” and it returned {"arm": "union_max", "budget": 100000, "mean_dti": 0.16087170045905524, "fold_wins": 4}. Budget is the one lever whose size is known from the metric's own algebra; everything else is a ranking bet.
