Why the "Predicted values must be in range [0, 1]" error happened, and why it can't happen here

Earlier family artifacts exported NaN in pixels outside the competition footprint; the portal's validator scans every pixel (including the NaNs) and rejects the upload. H60 writes the raster through src/gems52/grid.py::write_geotiff, which hard-fails the build if any pixel is non-finite or outside [0, 1], and the file is then re-read from disk to confirm before the link is posted. Concrete verified numbers for the H60 TIFF:

  • dtype: float32, 1 band
  • shape: 3730 × 3292 (matches sample_submission.tif)
  • CRS: EPSG:32611, pixel size 100 m × 100 m, transform identical to sample
  • NaN/Inf pixels: 0
  • min value: 0.0, max value: 1.0 (binary)
  • 0 pixels outside the footprint
  • 0 pixels on a labelled catalogue pixel; 0 pixels within 200 m of a mapped trace (the ring that earns zero credit per metric algebra — knowledge/01)

Rules refresher (official)

  • Competition home: https://www.drivendata.org/competitions/306/competition-doe-gems/
  • Problem description & metric: page/967 — DTI with α=0.2, β=0.8, triangular kernel R=300 m.
  • About page: page/968.
  • Submission format: single-band GeoTIFF (.tif), or a .zip containing one; must match the sample CRS, shape and geotransform; predictions in [0, 1]. NaN outside the footprint is technically allowed by the spec, but the form's validator has been observed to reject NaN, so H60 emits no NaN anywhere.
  • Three submissions per rolling 7-day window; your team decides whether a research-only file is worth a slot.

What you are committing when you upload

A pixel set of 31,000 binary fault-probability assertions at 100 m resolution over the 373 km × 329 km competition footprint. The TIFF is not a verified fault map; it is a ranked hypothesis set. Phase-2 geological review by the DOE reviewers decides which pixels correspond to real structures. The accompanying note says so explicitly.

Reproducing the build

bash scripts/download_competition_data.sh      # login-walled in production;
                                                # this checkout uses SHA-pinned mirrors
python3 scripts/prepare_data.py
PYTHONPATH=src python3 scripts/build_h60_submission.py

The build script writes the TIFF into submission/, copies a byte-identical alias into docs/downloads/h60-candidate.tif, and emits a full receipt to evidence/h60_build.json (also rendered as the H60 audit page).

What to do if the portal still rejects

  1. Re-download the ZIP from this page; older-family TIFs in your browser's download folder may contain NaN.
  2. Re-check the file locally with python -c "import rasterio,numpy as np; a=rasterio.open('h60-candidate.tif').read(1); print('finite',np.isfinite(a).all(),'min',a.min(),'max',a.max(),'shape',a.shape)". It should print finite True min 0.0 max 1.0 shape (3730, 3292).
  3. If the rejection message differs, open an issue on the repository with the exact message and the SHA-256 of the file you uploaded; do not silently re-upload a different file.
