The rules this page enforces

Quoted from the official problem page, “The Problem” (fetched 2026-10-09), under Submission format:

  1. Values in [0, 1]. “Predictions should be pixel-wise probabilities of fault presence, with values between 0 and 1.” This is the rule behind the rejection message Predicted values must be in range [0, 1].
  2. Single layer, 32-bit float. “a single layer GeoTIFF … 32-bit float”.
  3. Same projected CRS as the training data: UTM zone 11N, EPSG:32611.
  4. Same 100 m resolution and the same bounds as the training data; “the data outside the bounds is null or nan”.
  5. File type: a single-band GeoTIFF, or a ZIP archive containing one GeoTIFF.

What a FAIL here does and does not mean

A FAIL on a hard row means the file will be rejected by the submission form, or scored wrongly. It does not mean the prediction is good: format validity and scientific merit are separate questions, and the score each round earned is recorded separately as ORGANIZER-CONFIRMED or OWNER-REPORTED in the site home. An informational row (blue) never affects the verdict; it is there because the organiser's own template contains NaN pixels outside the footprint.

Privacy. This page runs entirely from static files on GitHub Pages. The check is performed by assets/tifcheck.js in your own browser: the file is read with the File API, decompressed and decoded locally, and no byte of it is transmitted. You can verify this in your browser's network panel — the only requests are for the HTML, the CSS inline above, and the one script.
