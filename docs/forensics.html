1. Mathematical Anatomy of the Official Distance-Weighted Tversky Index (DTI)

From the official DrivenData Problem Description (Page 967) and DOE GEMS Prize Official Rules (NREL/TP-5700-96647), let G ⊂ Ω denote the held-out unmapped ground-truth fault pixels (after masking the known USGS/INGENIOUS catalogue C of 60,988 pixels) and let p: Ω → [0, 1] be the submitted prediction raster. With linear triangular kernel k(d) = max(0, 1 - d/R) at radius R = 3 px = 300 m, α = 0.2, and β = 0.8: 

c(g) = max_{x in Omega} [ p(x) * k(||x - g||_2) ]
T(p) = sum_{g in G} c(g),      FN(p) = |G| - T(p)
FP(p) = sum_{x in Omega} p(x) * [ 1 - k(d(x, G)) ] = S(p) - M(p)

DTI(p) = T(p) / [ T(p) + 0.2 * FP(p) + 0.8 * FN(p) ]
       = T(p) / [ 0.2 * (T(p) + S(p) - M(p)) + 0.8 * |G| ]

Exact Marginal Inclusion Bar (src/gems52/metric.py): For a binary unit-mass dot added at pixel x with incremental numerator credit ΔT = Δ(T) and self-proximity credit ΔM, when ΔT ≈ ΔM each added dot increases the denominator by α = 0.2. Differentiating DTI yields the exact break-even rule: 

Delta_DTI > 0   <=>   Delta_T > alpha * DTI = 0.2 * DTI

At DTI = 0.2778, a dot improves the score if and only if its marginal expected credit satisfies ΔT > 0.05556. Any dot placed within dcat ≤ 2.0 px (200 m) of the masked catalogue C contributes ΔT ≈ 0 to off-catalogue truth G while paying the full +0.20 denominator penalty!

Why GEMSDOE32 Reached 0.2778

  1. Step 1 (0.1922 → 0.2600): Sub-sampling the dense H19_5 lineament ridges (121,131 dots) into discrete sparse dots (44,090 dots) exploited the R = 3 px kernel’s max operator: one dot every ~2.8 px captures 85%+ of continuous line credit at 1/3rd the false-positive cost.
  2. Step 2 (0.2600 → 0.2708): Removing the 3,891 dots at dcat = 1.0 px (100 m) saved 0.2 × 3,891 = 778.2 denominator penalty units.
  3. Step 3 (0.2708 → 0.2778 in GEMSDOE32): Removing the 2,545 dots at 1.0 < dcat ≤ 2.0 px (141–200 m) saved an additional 0.2 × 2,545 = 509.0 denominator penalty units while keeping the exact same 37,654 dots at dcat > 2.0 px (np.array_equal(d28 & (d_cat > 2.0), b2) == True).

How to Beat 0.2778 and Bridge to 0.3195+

Why did 0.2778 plateau below the 0.3195 leaderboard top score?

  • Frozen Legacy Backbone: All submissions from 0.2477 to 0.2778 were strict subsets of H19_5, which placed 2-px adjacent pairs (wasting ~5,000 dots to self-overlap within the 3 px kernel) and never used 3DEP LiDAR scarps or USGS GeoDAWN radiometric ratios.
  • Zero Co-Trained Disagreement Filtering: 0.2778 retains B-only flat-valley surface artifacts and misses buried intra-basin fault segments where surface topography is flat.
  • Submodular Expected-Credit Placement: Replacing static d2-8 grid subsampling with CELF lazy-greedy submodular optimization over the exact 300 m kernel increases off-catalogue SGMC coverage from 8.88% to 16.76% (Holdout LM 0.07404 → 0.12863, +73.7%).

3. Root-Cause Proof & Guaranteed Fix for "Predicted values must be in range [0, 1]"

We audited every band of data/training_features.tif, data/labels.tif, and data/sample_submission.tif to identify why submissions fail with the DrivenData portal error "Predicted values must be in range [0, 1]":

  • Cause A — 3,061 Unmasked -3.4028235e+38 Sentinel Cells Inside the Active Footprint: In training_features.tif, 13 of the 19 bands (mag_anom, rtp, tmi_hg, iso_grav_anom_slope, tc, tmi_vg, iso_grav_anom_vg, det_elev, iso_grav_anom, tmi, iso_grav_anom_hg, det_elev_slope) contain 3,061 cells equal to -3.4028234663852886e+38 inside the 5,167,373-pixel active footprint defined by np.isfinite(sample_submission.tif). Any feature transform that only checks np.isfinite(raw) treats -3.4028235e+38 as a valid finite number!
  • Cause B — Full-Grid Range Check Against NaN Outside the Footprint: In Python/NumPy, np.all((arr >= 0.0) & (arr <= 1.0)) evaluates to False if any pixel in the 3730 × 3292 array is NaN (because NaN >= 0.0 is False).

Our Dual-Layer Fix (src/gems52/features.py & src/gems52/submission.py):

  1. At ingestion, _read_clean_band masks raw <= -1e38 and imputes the in-footprint median before any spatial filtering.
  2. At export, write_submission_geotiff(..., mode="zeros") clips active footprint predictions to [0.0, 1.0], fills the 7,111,787 outside-footprint pixels with 0.0, writes single-band float32 with nodata=None, and runs verify_geotiff_on_disk to assert 12,279,160 / 12,279,160 finite pixels in [0.0, 1.0].
